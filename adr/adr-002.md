# ADR-002: Ingestão agendada, persistência local e API interna

- **Status:** Aceito
- **Data:** 2026-11-10
- **Atualizado:** 2026-11-13
- **Responsáveis:** Grupo 2

## Contexto

O Caixaverso Cotação deve obter cotações da API PTAX do BACEN, mantê-las em armazenamento local e disponibilizar o histórico por uma API interna para consumo por aplicações. No MVP, o escopo de dados compreende valores de compra e venda de dólar (USD) e euro (EUR), referentes aos boletins de abertura e encerramento; os boletins intermediários das 11h e 12h não fazem parte do armazenamento inicial.

A API interna é necessária para o MVP. Ela deve consultar os dados locais, sem depender de chamadas ao BACEN no fluxo da consulta. Em 2026-11-13, o grupo confirmou que o projeto será somente backend: não haverá página web, frontend ou gráficos.

## Decisão

Adotar o fluxo **BACEN PTAX → coleta assíncrona agendada → persistência local em H2 → API interna somente de leitura → consumidores internos**. H2 substitui PostgreSQL, conforme decisão do grupo registrada na Constituição do Projeto.

- **Coleta:** o job usa Quarkus Scheduler e MicroProfile REST Client para consultar a API PTAX conforme o agendamento aprovado, identificar os boletins esperados para moeda e data e persistir compra e venda em H2 por repositories Panache. Tentativas, recuperação de pendências e integridade dos dados seguem as regras de negócio aprovadas.
- **Persistência:** H2 embarcado em arquivo persistente é a fonte local consultada pela API. Flyway versiona o esquema e Hibernate o valida, sem recriação na operação normal. A API não acessa o BACEN para completar ou atualizar uma consulta.
- **API do MVP:** disponibilizar uma API interna com Quarkus REST, somente de leitura, para consultar histórico por moeda e período. A API deve contemplar os valores disponíveis dos boletins de abertura e encerramento e tornar explícitas as lacunas ou a disponibilidade parcial. DTOs próprios, e não entidades JPA, compõem o contrato HTTP.
- **Canal de consumo:** a API é parte obrigatória do MVP e o único canal de consulta do produto. Acesso direto ao banco e página web não são entregas do projeto; acesso técnico para testes e manutenção não constitui um canal de consumo.
- **Separação de responsabilidades:** a coleta e a consulta são responsabilidades lógicas distintas dentro de um único aplicativo Quarkus, executado em um único processo JVM no MVP.
- **Limite das decisões:** quantidade e caminhos exatos dos endpoints, nomes e tipos dos parâmetros, formato da resposta, estados de disponibilidade, erros, status HTTP e mecanismos de autenticação e autorização serão definidos no contrato da API. Como ponto de partida para o MVP, recomenda-se um endpoint de histórico por moeda e período que inclua os boletins disponíveis de abertura e encerramento; não é necessário separar endpoints apenas pelo tipo de boletim.
- **Topologia do MVP:** um único processo JVM executa job e API e acessa o mesmo H2 embarcado em arquivo. Quando executado em Docker, usar um único container da aplicação com volume persistente para o banco; Docker Compose organiza a execução local. Não compartilhar o arquivo H2 entre processos ou réplicas da aplicação. Caminho do arquivo, volume, backup, retenção e ambiente de implantação permanecem pendentes; processos separados ou múltiplas réplicas exigem revisão arquitetural.
- **Proteção contra coleta sob demanda:** não haverá chamada síncrona ao BACEN no fluxo de consulta. A ausência de dados locais não inicia coleta em resposta ao consumidor.

## Consequências

- **Benefícios:** os consumidores internos usam uma interface de consulta estável; a consulta fica desacoplada da disponibilidade momentânea do BACEN; os dados coletados são reutilizados a partir da persistência local.
- **Custos e riscos:** o histórico pode estar atrasado ou incompleto se houver falha ou atraso na publicação ou na coleta. São necessários controles de pendência, prevenção de duplicidade, observabilidade e uma representação clara de dados ausentes ou parciais.
- **Operação:** o arquivo e o volume persistente do H2 devem sustentar o acesso do único processo e sobreviver a reinícios. O MVP não oferece escalabilidade horizontal; separar job e API ou adotar múltiplas réplicas exige revisar banco e topologia. Quarkus Scheduler não preserva automaticamente as pendências de negócio; seu estado e retomada devem ser definidos conforme RNF-006.
- **Escopo:** não há implementação de frontend ou endpoints de escrita para consumidores. A separação entre DTOs e entidades permite evoluir o esquema sem alterar implicitamente a API.
- **Contrato da API:** permanece necessário definir no contrato os filtros de moeda e período, a representação dos boletins, a disponibilidade, os dados parciais, os erros e o controle de acesso. A sugestão de um endpoint único é uma orientação para o MVP, não a especificação final da rota ou do payload.
