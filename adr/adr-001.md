# ADR-001: Stack do projeto — Java 25, Quarkus 3.40 LTS e extensões

- **Status:** Aceito
- **Data:** 2026-11-09
- **Atualizado:** 2026-11-13
- **Responsáveis:** time/caixa

## Contexto

O Caixaverso Cotação precisa de uma stack definida para orientar o desenvolvimento e produzir builds reproduzíveis. O grupo aprovou Java 25 e Quarkus 3.40 LTS para este projeto, alinhando-se à diretriz corporativa informada ao grupo. Em 2026-11-13, definiu os componentes de REST, persistência, cliente HTTP, agendamento e evolução do banco e delegou as escolhas complementares à IA, com preferência por Quarkus e SmallRye.

Esta decisão se aplica ao Caixaverso Cotação. Ela não estabelece uma política de migração para outras aplicações. A referência documental específica da diretriz corporativa não está identificada neste repositório e deve ser registrada quando estiver disponível.

## Decisão

- Adotar **Java 25 (JDK 25)** para o desenvolvimento do Caixaverso Cotação.
- Adotar **Quarkus 3.40 LTS** como framework do projeto.
- Limitar o escopo desta decisão a este projeto; a atualização de aplicações existentes está fora deste ADR.
- Adotar **Maven 3.9.16**, fixado com Maven Wrapper. Fixar o patch do BOM Quarkus 3.40 e validar JDK, plugins e dependências ao preparar a implementação, sem sobrescrever versões gerenciadas pelo BOM por padrão.
- Implementar a API com **Quarkus REST** e **Jackson**, sem RESTEasy Classic.
- Usar **Hibernate ORM com Panache no padrão Repository**, por `PanacheRepository` ou `PanacheRepositoryBase` conforme a chave aprovada. Não gerar endpoints CRUD a partir das entidades.
- Consumir o BACEN por **MicroProfile REST Client**, usando a implementação **Quarkus REST Client** e Jackson.
- Executar os jobs com **Quarkus Scheduler**. Quartz não faz parte do MVP; a recuperação das pendências de negócio é uma responsabilidade explícita da aplicação.
- Versionar o esquema com **Flyway** e usar Hibernate para validá-lo, sem recriar dados na inicialização normal.
- Estruturar DTOs com **records do Java** e entidades JPA com classes. Usar mapeamentos explícitos entre DTOs do BACEN, entidades e DTOs da API, sem Lombok ou MapStruct no MVP.
- Validar dados com **Jakarta Bean Validation / Hibernate Validator** e tratar falhas técnicas com **SmallRye Fault Tolerance**, sem substituir a política de tentativas agendadas da RN-005.
- Documentar a API com **SmallRye OpenAPI**, seguindo OpenAPI 3; habilitar Swagger UI somente em desenvolvimento e testes.
- Adotar **Quarkus OIDC** para autenticação por bearer token e autorização por perfis. Provedor, perfis e configuração de credenciais permanecem sujeitos ao contrato da API, sem presumir SSO interativo.
- Adotar **logs JSON do Quarkus**, **SmallRye Health** e **Micrometer / Prometheus**. Destino dos registros, alertas e metas operacionais permanecem pendentes.
- Usar **JUnit 5, QuarkusTest, REST Assured, Mockito e WireMock**, com H2 nos testes de persistência, e **GitHub Actions** para build e testes pelo Maven Wrapper.
- Priorizar extensões oficiais do Quarkus e implementações SmallRye adequadas. Fixar as versões externas não gerenciadas pelo BOM antes da implementação correspondente.
- O banco H2, a API somente de leitura, a ausência de frontend e a topologia do MVP seguem o ADR-002. A lista de extensões e as responsabilidades estão detalhadas no Plano Técnico.

## Consequências

- **Benefícios:** fornece uma base tecnológica comum e explícita para desenvolvimento, build e testes, com integração pelas extensões do Quarkus e separação entre persistência e contratos HTTP.
- **Custos e riscos:** dependências, plugins de build, ambiente de execução e pipeline de testes precisam ser compatíveis com as versões escolhidas. OIDC exige um provedor aprovado; escolher a extensão não define sua configuração ou os perfis autorizados.
- **Acompanhamento:** fixar e validar as versões efetivamente usadas no build. Registrar a fonte corporativa específica quando identificada. Escolhas de tecnologia não resolvem parâmetros operacionais nem aprovam comportamentos HTTP pendentes.
